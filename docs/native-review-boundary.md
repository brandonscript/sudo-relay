# Native review and receipt boundary

November 10, 2026. Receipt-only experiment, using the existing macOS Touch ID lab. No broker connection, command execution, sudo password, service installation or persistent key enrollment. The inline card remains a preview; this is not a replacement for the accepted chat design or a requirement to use biometrics.

## What changed

The original Touch ID trial signed data generated by its own UI. The new trial separates three responsibilities in code:

1. A receipt authority stores a frozen request and signs its exact bytes with an ephemeral Ed25519 key. The request includes a fresh enrollment, machine label, nonce, expiry, command arguments and authentication mode.
2. The native reviewer verifies the authority signature against a pinned public key before decoding or displaying anything. Display and signing use the same immutable request. The reviewer selects output sharing and freezes that decision before requesting a biometric-protected P-256 signature.
3. An independent verifier object compares the decision with its own stored request and enrolled public key. It rechecks expiry, rejects weaker authentication modes, and consumes one receipt atomically under a lock. It does not accept an ID, digest or `human=true` assertion as approval.

The fixture creates and directly wires both key identities at startup. That simulates trusted enrollment; it does **not** implement it. In production, never accept an authority key alongside an untrusted request as its own proof of identity. The verifier accepts a key signature, not hardware attestation: assurance about Touch ID depends on the protected enrollment process creating the key with the required access controls.

This lab uses a separate, canonical JSON domain, incompatible with the broker protocol. It rejects unknown/duplicate/noncanonical fields, oversized requests, relative executables, control characters and non-ASCII command arguments rather than displaying ambiguous content. That restricted input set is a lab limit, not a proposed general shell policy. Script and environment support are intentionally absent.

## Automated cases

Run `swift test -Xswiftc -warnings-as-errors` in `security-lab/touch-id`. Tests use throwaway software keys, no biometric prompt or real signing credentials.

| Case | Attempt | Required result |
|---|---|---|
| NR1: authenticated review | Wrong authority key or altered command with original authority signature; valid original as control. | Reject before creating the review model; original renders exact, quoted argv. |
| NR2: misleading/unsupported input | Signed downgrade, wrong domain/machine, relative path, bidi/newline argument, oversized argument/request, invalid limits, extra fields. | Reject even with a valid authority signature. |
| NR3: exact decision | Change output choice, request, authentication mode or add fields; use another signer. Also sign a substituted request or downgrade with the enrolled key. | Reject; unchanged decision still accepted. A valid signature alone is insufficient. |
| NR4: one use | Submit sixteen concurrent copies, then transfer proof to a fresh verifier/enrollment. | One receipt total; new verifier rejects the old proof. |
| NR5: cancellation and time | Prepare proof, deny or expire before receipt consumption; attempt review before creation or signing at expiry. | Reject late proof and invalid time window. |
| UI layout | Build the actual native accessory view; inspect frames, read-only summary, sharing default and absent number field. | Nonzero frame, visible child controls inside its bounds, command from authenticated data, sharing off; countdown and disabled controls at expiry; Return assigned to Approve. This checks construction, not actual screen rendering. |
| Command rendering | Include empty, spaced, quoted and shell-looking arguments. | Display quoting preserves argument boundaries; nothing is interpreted or executed. |

All seven new cases and the three existing native tests passed locally with Swift compiler warnings treated as errors. This is verification of the protocol/state logic, not proof of process isolation, hardware enforcement or what a human saw. Existing macOS CI runs the same test target.

## Manual runbook

Build the existing `touch-id-probe`, then run `touch-id-probe --review-boundary` as an ordinary user. The test never accepts caller-supplied command bytes or a signing key. The researcher must not enter the number, approve the native review, or complete the OS prompt for the participant.

| Case | Human action | Evidence to record |
|---|---|---|
| NR6: positive control | Read the command and machine, inspect Details if needed, optionally enable output sharing, approve and complete Touch ID. | Request readable; observed fingerprint prompt; native review closes; process output records one verified receipt with selected sharing value and replay rejection. No command runs. |
| NR7: native denial | Start a fresh process and choose Deny. | Zero receipts, no authentication fallback. |
| NR8: authenticator cancellation | Start fresh, approve review, cancel the OS prompt. | No receipt; experiment stops, no session/password fallback or automatic retry. |
| NR9: delayed authentication | Let expiry pass while review or authentication is pending. | No receipt even if a late signature is returned. |
| NR10: review manipulation | In a separate contained deployment, use each authorized automation/IPC route to alter the native review or submit a decision directly. | Record actual access and receipt count; no human-only claim from an unavailable tool. Requires protected installation and an independent verifier before meaningful adversarial deployment testing. |

The first NR6 attempt exposed an AppKit layout bug: the accessory stack had a zero-sized frame, hiding review/number controls while leaving approval enabled. Clicking approval failed validation before signing. An explicitly sized native view fixed it, with a regression test. The participant then reported visible fields, successful Touch ID and “One receipt verified.” The captured process log independently showed the noninteractive signing attempt rejected (`com.apple.LocalAuthentication -1004`), but did not include the receipt line; the positive result is therefore participant-reported, not a separately recovered receipt. Receipt/denial evidence now uses unbuffered writes. Later instrumentation captured an interactive signature returning but no verifier result before process exit. Treat those early reports as provisional. The native entry point and verifier call were changed from an async/actor handoff to synchronous AppKit execution with locked one-use state; the sixteen-way concurrency test still passes. The exact framework/runtime cause of the early exit was not independently isolated.

The participant requested a shorter review and no number entry for Touch ID. The native flow now omits the attention code entirely, uses a compact native panel with a 24-point shield/title, a default Return-key approval button, an approval countdown and a visible purpose. Only the command is code-formatted; machine information sits outside it and technical data, including the execution timeout, stays under Details. The chat/session card is unchanged. Signature, request, mode and expiry checks remain mandatory. NR6 subsequently passed as recorded below; NR7–NR9 and NR10 remain pending. Do not change fingerprints, Keychain settings, OS permissions or real account policy for this trial.

## Verified native control and final UX

After the synchronous verifier change, the participant confirmed the layout and provided a screenshot of “One receipt verified.” The process independently logged interactive signing, receipt `712B75B5-CF6C-469F-89C7-A2AC7026A627`, decision digest `4ea993fa2abcd82fe197a0f632015921b0aa0fb65639892ceb05bc982ce3a9ba`, sharing off, and rejected replay. It also logged the no-interaction signing attempt rejected with `com.apple.LocalAuthentication -1004`. The process exited successfully. No command ran.

At the participant's request, the native flow now closes after successful verification or denial, without a third success/Close dialog. Receipt evidence remains in process output; removing those two informational dialogs does not change signing or verification. This final presentation-only deletion has automated/build coverage but has not had another hardware run. The future chat adapter should show Approved/Denied and authoritative execution status in the card; this lab has no such integration yet.

The visible lab labels identify a fake local machine and receipt-only behavior. A production subtitle should identify the authenticated target and execution account, for example `home-server · Linux · Run as root`; presentation metadata such as “inline-only” need not be user-facing. Keep the lab's no-execution label until an actual production integration exists.

## The deployment boundary still to build

The reviewer and verifier currently run in the same ordinary-user development process. Its source and executable are agent-writable. A lock prevents concurrency races; it is **not** a security boundary. Keys and receipt state are ephemeral; exit discards them. There is no durable ledger, crash recovery, protected pairing, revocation or recovery flow. Do not connect this process to root execution or advertise its code structure as isolation.

For the stronger Mac option, the candidate deployment is a signed, hardened native reviewer with a biometric-protected key, an independently protected verifier/enrollment store, and authenticated IPC. Authenticate both peer code identities using narrow requirements; a matching UID, PID or an application name is insufficient. Opening a review or receiving an IPC call must never sign by itself. The helper fetches authoritative request data; the chat supplies only an opaque request reference. Review changes require a new decision and confirmation.

Apple documents enforcing [code-signing requirements on XPC peers](https://developer.apple.com/documentation/foundation/nsxpcconnection/setcodesigningrequirement(_:)) and [narrow identity requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements/). These support the proposed deployment mechanism; they do not establish resistance to every accessibility, injection or display-spoofing route. Apple also documents [Secure Enclave key access controls](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave). Signing identity, supported OS versions, entitlements, installation protection and actual peer-rejection tests remain unverified. No certificate or account provisioning was attempted.

Passkeys remain optional. The session-only mode continues to attest an authenticated session, not independently verified human presence. It cannot inherit the Touch ID mode's assurance and must never be selected automatically after a failed biometric ceremony. If all review must stay inline, we still need a host-enforced protected confirmation channel; inline-only presentation metadata alone does not provide that guarantee.

## Execution-timeout follow-up

Approval expiry is the deadline to authorize a request; it does not determine how long a launched command may run. The existing broker already accepts a signed per-request `timeout_secs`, with a hard-coded 1–300 second range and a 300-second default. This native fixture fixes that value to 30 seconds and never executes. The main review now omits it at the participant's request; Details retains it.

For long-running work, evaluate a separately configured administrator maximum and a per-request duration bounded by it. Keep the chosen value in the frozen/signed request, require fresh approval to change it, and test runtime limits independently from approval expiry. No production timeout limit was changed in this work.
